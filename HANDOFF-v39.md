# HANDOFF v39 — Training Log

Covers the tail end of the configurable-training-days-per-week feature, on `claude/configurable-workout-days-oj3t4r`, merged to `main` at **v3.213**. This branch has no prior HANDOFF of its own — the last few HANDOFFs (v33/v36/v37/v38) documented a *different* line of work (citation-currency/exercise-research-alignment) on a separate branch. Read this one for anything related to per-program day-count plans or the archive-week button; read v38 (and its own "what's still open") for the citation-audit line of work, which this session did not touch.

## 1. What this feature is, end to end

A user-facing "Training days per week" preference (Profile screen, 1-7, blank = program default). Selecting a count doesn't just repeat existing sessions — every count from 1 through 7 has its own hand-authored, frequency-appropriate plan per program (`PROGRAM_DAY_COUNT_VARIANTS` in `index.html`), reasoned from that program's own cited research about what to add/skip at low vs. high frequency. This shipped across 11 batches over multiple sessions; **this session shipped the last two (10 and 11) and closed the rollout out completely.**

## 2. What shipped this session

**Bug fix (2 rounds) — "Save this week & start fresh" archive button.** Found via user report while working batch 10. The button used to live inline inside `renderWorkout()`'s rest-day branch, gated on `activeDay === 'd7' && day.rest` — which meant it was completely unreachable on every 6/7-day variant across ~20 programs, since Day 7 becomes a real training day at those frequencies. Round 1: moved it to a persistent `#archiveWeekWrap` sibling of `#exerciseList`, visibility toggled by a new `renderArchiveWeekVisibility()` keyed on `activeDay` alone. Round 2 (user correction): the fix still hardcoded `'d7'`, ignoring the pre-existing drag-reorder feature (`dayOrder`) — a user who reorders their days so a different day lands in the last tab slot would still see the button on the now-wrong day. Fixed to check `activeDay === dayOrder[dayOrder.length - 1]` instead. Both rounds are real-invocation + sabotage tested (`test-archive-week-visibility.js`, 6 tests) and live-verified in headless Chromium, including actually entering reorder mode and dragging the last tab to a new position.

**Batch 10 — Watersports (6 disciplines): Surfing, Skimboarding, Wakeboarding, Kite-Assisted Surfing, Stand-Up Paddleboarding, Kayaking.** Third style-variant container (after Cycling/Combat). Each discipline's high-frequency extra day deliberately avoids that discipline's own highest-injury-risk exercises per its own citation (no Box Jump/Broad Jump/Single-Leg Bound on Surfing's extra day, matching its shoulder-injury citation; no Box Jump/Broad Jump on Wakeboarding's, matching its 42.3% ACL-tear citation; etc.). SUP and Kayaking both get "Extra Shoulder Health & Core Endurance" at 6/7 days, tied to each one's own most-commonly-injured-site citation. PR #14, merged.

**Batch 11 — Yoga (3 styles): Vinyasa & Flow, Hot Yoga, Partner Yoga. Fourth and final style-variant container — rollout complete.** Flow/Hot use their two highest-intensity days (Vinyasa + Power) as the low-frequency pillars and never add a 2nd hard session at high frequency; Hot's extra day specifically stays unheated (its own citation found heat doesn't clearly out-perform non-heated practice, so the extra day doesn't add cardiovascular/heat strain the research doesn't support). Partner Yoga's extra day stays gentle — its own non-negotiable rule ("the person being stretched sets the depth, always") applies at every frequency, not just the default. PR #15, merged.

**Net result: every non-medical program in the app (24 of 25, counting each style inside a container as covered by it) now has a real per-day-count plan.** The 13 medical/rehab programs remain permanently excluded — a clinical-progression decision, not a frequency-optimization gap (unchanged from earlier batches, re-confirmed this session, not relitigated).

## 3. Architecture, for whoever touches this next

- `DAYS_PER_WEEK_PROGRAMS` — flat list of every program key this feature covers (24 entries as of this session).
- `DAYS_PER_WEEK_STYLE_CONTAINERS` — the 4 keys (`cycling`, `combat`, `watersports`, `yoga`) whose `.days` is swapped at runtime by sub-style, not fixed. Excluded from `DAYS_PER_WEEK_ORIGINAL`'s snapshot for that reason.
- `getStyleContainerAccessor(key)` — one function, one branch per container, returns `{styles, activeStyle}`. Started as a cycling-only special case, generalized to combat in batch 9, now covers all 4. Adding a 5th container (there isn't one left, but if the app ever gains one) means: one branch here, one line in `DAYS_PER_WEEK_STYLE_CONTAINERS`, one entry in `DAYS_PER_WEEK_CONTAINER_DEFAULT`, that container's own `PROGRAM_DAY_COUNT_VARIANTS` entry, and its style-switch handler (`render*Selector`) needs to call `applyDaysPerWeekProgramData()` instead of directly assigning `.days` — get that last part wrong and a style switch silently discards whatever day-count pref was active (this exact bug was fixed for Watersports's and Yoga's selectors this session, mirroring the fix Combat needed last session).
- `applyDaysPerWeekProgramData()` — single function, one generic branch for flat programs, one generic branch (via the accessor) for containers. Already fully generalized; no further changes needed for future containers to reuse it.
- Every high-frequency (6/7-day) extra day, across every batch shipped so far, follows the same rule: never a repeat of the program's own hardest/highest-injury-risk session. What "genuinely lower-toll" means is decided per-program from that program's own cited research, not a generic template.
